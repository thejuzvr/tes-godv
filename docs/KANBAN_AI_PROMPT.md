# Kanban-доска: JSON-массив задач и промпт для AI-генерации

Файл описывает формат JSON-массива карточек Kanban-доски и готовый промпт,
который можно вставить в любую AI-модель, чтобы получить валидный массив задач.

---

## 1. Формат

Корень документа — **JSON-массив объектов** (карточек доски). Колонки доски
фиксированы и кодируются строкой `column`:

| Значение `column` | Колонка     | Роль      |
|-------------------|-------------|-----------|
| `develop`         | Разработка  | developer |
| `analysis`        | Анализ      | analyst   |
| `producer`        | Продюсер    | producer  |

### Схема одной карточки

```json
{
  "id": "c-001",
  "title": "Короткий заголовок задачи",
  "description": "Что нужно сделать: детали, критерии готовности.",
  "column": "develop",
  "priority": "high",
  "review": {
    "verdict": "pending",
    "comment": ""
  },
  "history": [
    { "at": "2026-02-14T12:00:00Z", "column": "develop", "note": "Карточка создана" }
  ],
  "createdAt": "2026-02-14T12:00:00Z",
  "updatedAt": "2026-02-14T12:00:00Z"
}
```

### Поля

| Поле        | Тип     | Обязательно | Правила |
|-------------|---------|-------------|---------|
| `id`        | string  | да          | Уникальный, формат `c-NNN` (три цифры, без пропусков нумерации) |
| `title`     | string  | да          | 5–80 символов, глагол в инфинитиве («Добавить…», «Пересмотреть…») |
| `description` | string | да        | 20–500 символов; конкретика, что и где менять |
| `column`    | string  | да          | Один из: `develop` \| `analysis` \| `producer` |
| `priority`  | string  | да          | Один из: `low` \| `medium` \| `high` |
| `review.verdict` | string | да      | `pending` \| `pass` \| `fail` |
| `review.comment` | string | да      | Непустая строка **только** когда `verdict` = `fail` или `pass`; иначе `""` |
| `history`   | array   | да          | Хронология перемещений, минимум 1 запись; `at` — ISO-8601 UTC с `Z` |
| `createdAt` | string  | да          | ISO-8601 UTC с `Z`, равна первой записи `history` |
| `updatedAt` | string  | да          | ISO-8601 UTC с `Z`, равна `at` последней записи `history` |

### Правила цикла проверки (инварианты)

1. Жизненный цикл: `develop` → `analysis` → `producer`. Карточка в `producer`
   с `verdict: "pass"` считается завершённой.
2. **Loop проверки:** если `verdict` = `fail`, карточка обязана быть в
   `develop`, а `review.comment` — содержать причину отказа. Повторный заход в
   `analysis` допускается: тогда в `history` появляется вторая запись
   `analysis`, а `verdict` сбрасывается в `pending`.
3. `verdict: "pending"` допустим только в `analysis` (ждёт проверки) или
   `develop` (проверки ещё не было). В `producer` — только `pass`.
4. Порядок записей в `history` — по возрастанию `at`; `updatedAt` = `at`
   последней записи.
5. Нумерация `id` непрерывна: `c-001`, `c-002`, … без дублей и пропусков.

## 2. Промпт для AI (скопировать целиком)

```text
Ты — продюсер проекта TES Idle (Elixir/Phoenix backend + React frontend idle-игра
по мотивам Skyrim). Твоя задача — подготовить бэклог задач для Kanban-доски
команды из трёх ролей: разработчик (develop), аналитик (analysis), продюсер
(producer).

Верни СТРОГО валидный JSON-массив карточек без каких-либо пояснений до или
после массива — только массив.

Контекст задач: [ОПИШИ ТЕМУ ЗДАСЬ, например: "улучшение панели гильдий",
"новая система питомцев", "доработка карты мира"].

Требования к каждой карточке:
- id: уникальный "c-001", "c-002", ... нумерация без пропусков;
- title: 5-80 символов, начинается с глагола в инфинитиве;
- description: 20-500 символов, конкретное описание что и где менять
  (упоминай модули/файлы, если уместно);
- column: "develop" | "analysis" | "producer";
- priority: "low" | "medium" | "high";
- review: объект { "verdict": "pending" | "pass" | "fail", "comment": "..." };
  comment непустой только при verdict "fail" или "pass";
- history: массив перемещений { "at": ISO-8601 UTC c "Z", "column": "...",
  "note": "..." }, минимум одна запись, по возрастанию времени;
- createdAt: равна "at" первой записи history;
- updatedAt: равна "at" последней записи history.

Правила цикла проверки:
- обычный путь: develop -> analysis -> producer;
- если анализ провалил карточку (verdict "fail"), карточка обязана вернуться
  в "develop" с непустым comment; после доработки она снова идёт в "analysis"
  (вторая запись analysis в history, verdict снова "pending");
- карточка в "producer" может иметь только verdict "pass";
- у части карточек (примерно 1 из 4) должен быть показан один виток
  провала: fail в analysis -> возврат в develop -> повторный analysis ->
  pass -> producer. Такой виток отражается в history и review.

Сгенерируй от 6 до 10 карточек. Приоритеты распредели реалистично
(не всё "high"). Даты: используй текущую дату и время, шаг между
перемещениями 30-180 минут, карточки созданы в разное время.

Вывод: только JSON-массив, без markdown-обёрток и комментариев.
```

## 4. Проверка массива после генерации

Перед использованием убедись:

- [ ] корень — массив, не объект;
- [ ] каждый `column` — из трёх допустимых значений;
- [ ] нет карточек `verdict: "fail"` вне `develop` и `verdict: "pass"` вне `producer`;
- [ ] `id` уникальны и непрерывны (`c-001`, `c-002`, …);
- [ ] у карточек с `fail`/`pass` непустой `review.comment`;
- [ ] `history` отсортирована по `at`, `createdAt`/`updatedAt` согласованы;
- [ ] у ~1 из 4 карточек виден виток провала (fail → develop → analysis → pass).
